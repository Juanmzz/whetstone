# Whetstone

**Self-sharpening standards for coding agents.**

## Thesis

A project's definition of *correct* should be executable, enforced where it matters, and should
sharpen with use — leaving an audit trail of why every rule exists.

Most of what a senior engineer does to guarantee quality is already deterministic: tests, linters,
type checks, hooks, review checklists. The LLM's unique contribution is **judgment**. So the split
should follow that: a deterministic **engine** does the mechanical 80% — cheap, reproducible,
reliable — and an **agent** is applied to the remaining 20%, and only where the change is critical.
Senior-grade rigour without paying senior-grade tokens on every line.

The second half of the thesis is the loop. Rules born from real friction beat rules written in
advance, so Whetstone records the friction it hits, distills it, and proposes the guardrails that
project actually needs — with a human gate and a receipt.

## The problem

Spec-driven development tools (Spec Kit, BMAD, Superpowers) solve the *forward* path well: spec →
plan → code, with human gates. Two gaps remain.

**Verification is advisory.** A `CLAUDE.md` full of rules is a suggestion — the model reads it and
hopefully complies. There is no mechanism that makes a non-negotiable non-negotiable, no way to
say "this check may block, that one may only warn", and no way to skip re-checking code that did
not change.

**The feedback path does not exist.**

- No project-level memory of decisions and signals that survives sessions and tools.
- No versioning of workflow rules — no diff, no changelog, no record of *why* a rule changed.
- No mechanism for the workflow to propose its own improvements based on what actually happened.

Every team that runs agents seriously ends up rebuilding this by hand, inside one tool, coupled to
one memory backend.

## What Whetstone is

A layer you apply to a repo, versioned as plain files in git.

1. **A definition layer** (`.wst/`) — the project's constitution, its risk triage, and a registry of
   the checks that matter. Generated by an interview at `wst init`, amended by the retro.
2. **A deterministic engine** (`wst`) — it reads those definitions and does the mechanical work:
   classify each change by criticality, select the checks that apply, skip what receipts prove is
   unchanged, run the rest, and enforce the gate.
3. **A calibrated judgment boundary** — the engine shells out to an agent only for checks that are
   genuinely judgment, and only when the change is critical. A judgment check must prove itself
   stable over fixtures before it is allowed to *block* anything; otherwise it can only warn.
4. **Reviewable output** — every task ends in a PR annotated by criticality (🔴 review · 🟡 skim ·
   ⚪ skip), so human review still scales as it is trusted less.
5. **A retro loop** — signals accumulate, patterns get distilled, and the tool proposes new or
   amended checks. A human approves; the change lands with a changelog linking back to the evidence.

The loop: **use → record → distill → amend.** That is the moat.

```
.wst/
  constitution.md          # project governance
  triage.yaml              # risk classification, read by the engine
  triage-rules.md          # the same rules as documentation
  wst.yaml                 # which judge, which memory backend
  base.json                # what init wrote, so update can say what changed
  checks/                  # the check registry — one file per check
  memory/
    decisions.md           # every decision, by anchor id — what it ruled out, and why
    signals.jsonl          # append-only structured signal log
    retro-log.md           # what each retro proposed, and what was accepted
  skills/                  # versioned workflow rules, each with a changelog
```

## What Whetstone is NOT

- **Not another spec-driven framework.** It composes with Spec Kit, BMAD, Superpowers, or a bare
  `CLAUDE.md`. It owns the definition-and-verification layer, not your spec format.
- **Not a memory server.** Memory is an interface, not a product. **One backend ships: plain files
  in git**, and a second arrives when something needs what a file cannot give. Measured here at 58
  signals: the retro's clustering carries on the rule a signal implicates, which a string match
  over a file answers exactly. A semantic backend would improve the other axis, which is the one
  that does not decide anything. Which verbs the port carries is a question for `MemoryPort`, not
  for this page.
- **Not autonomous self-modification.** Every amendment to a rule passes a human gate. The value is
  *auditable* evolution, not unsupervised drift.
- **Not a fleet manager.** Whetstone triages a change and gates it. It does not brief, dispatch,
  schedule, supervise or scale an agent fleet; execution and judgment go to `claude`, GitHub to
  `gh`. It gates work from any source, which is more than it could reach if it launched the work
  itself.
- **Not tied to Claude Code.** Files-first design means any agent that reads markdown can consume
  it, and the LLM boundary is one port with swappable adapters. Claude Code gets first-class
  support (hooks, commands).

## Design principles

1. **Git-native.** All state is plain text in the repo. Diffable, reviewable, portable. No required servers.
2. **Memory-agnostic.** File backend by default; everything else is an adapter.
3. **Human-in-the-loop, triage-gated.** The retro proposes; the human disposes. On the forward path,
   autonomy is inverse to criticality — critical changes keep a human gate, trivial ones do not.
4. **Rules carry receipts.** Every rule and every check links to the signals and decisions that
   created it. Delete the reason, question the rule.
5. **Determinism by default.** The LLM is called only where judgment is irreducible. The engine's
   core cannot call one — the architecture enforces it, not discipline.
6. **A judgment check earns its `block`.** Deterministic checks may block freely. A non-deterministic
   one must first prove it is correct and stable over fixtures. A flaky gate is worse than no gate:
   it gets routed around, and then its value is negative.
7. **Small core, composable edges.** The core is the `.wst/` schema, the gate, and the retro loop.
   Integrations live at the edges.

## Milestones

**M1 — Bootstrap (v0.1)** ✅
Init procedure + `.wst/` schema + generic versions of the initial skill set, extracted from a real
production setup. Manual signal logging. Dogfooded on a real project.

**M2 — Code tier (v0.2)** ✅
The emitter compiles `.wst/` into per-vendor apparatus — hooks first (a project-specific
`strict-path-guard`, derived from `triage-rules.md`), then commands, earned via the retro.

**M3 — The retro loop (v0.3)** ✅ *(first pass)*
Pattern detection over `signals.jsonl` + `decisions.md`, apparatus recommendation, human approval,
changelog with signal receipts. Validated in the wild — a real project's signals produced the first
earned rule. Still N=1; repeatability is unproven.

**M4 — The engine (v0.4)** ← *current*
The Wizard-of-Oz procedures become code: `wst` CLI, deterministic core, the calibrated LLM boundary,
the check registry, the lean gate with receipts, and the annotated PR. Sequenced so the gate — the
differentiator — arrives before the convenience wrappers.

**M5 — Update model**
Keep bootstrapped projects current via 3-way merge against a recorded base; contribute local
amendments upstream — the same machinery in three directions.

**Later / explicitly deferred**
Distribution (`npx wst`, optional plugin). Then semantic search backends, multi-repo/org-level
memory, and a library of battle-tested paths that `init` can recommend from rather than
generating each project from scratch. A second judge adapter is no longer deferred: `gemini`
ships, and a check names which judge runs it.

## Contribution model

MIT license. The anti-scope section above is enforcement policy: PRs that turn Whetstone into a spec
framework or a memory server will be redirected, kindly.

## Origin

Extracted from a production workflow built for a fintech codebase (SDD orchestration, delegation
harness, TDD discipline, token economy — all born from real signals). Whetstone is the
generalization of that loop.
